# Moloco IAA SMB 项目
## 2026 年 Q3 运营总览与工作方案

> **用途：** 本文档是 Moloco IAA SMB 项目在 2026 年 Q3 的统一运营参考。文档说明项目目标、工作模式、各团队职责，以及如何将一个数据信号推进为可验证业务结果的规则。

## 1. 项目目标

本项目识别具备潜力的中小移动开发者，并建立一条可复制的路径来推动 Moloco 飞轮的两端增长：

- **Supply（供给侧）：** 协助合适的 Publisher 评估并接入 Moloco Publisher SDK，带来更多 IAA 供给；以及
- **Demand（需求侧）：** 识别同一开发者可能使用 Moloco DSP 进行用户获取（UA）的机会。

Q3 是一个运营模式验证季度。目标是让 Intelligence、Moloco Sales、GatherOne 和 Supply 跑通一套有纪律、可复制的联合工作机制，而不只是往名单中增加更多公司。


## 2. 工作模式

本项目采用清晰的双通道覆盖模式。

- **Moloco Sales** 负责战略关系判断、客户引荐，以及需要由 Moloco 直接覆盖的账号。
- **GatherOne** 负责可规模化的 SMB 触达、日常跟进、客户更新，以及机会被释放或分配后的执行。
- **Supply** 在机会需要时提供 Enablement、技术指引和升级支持；Supply 不负责日常 SMB 客户挖掘。
- **Intelligence** 提供候选客户 Pipeline、数据背景、优先级判断和结果验证。

```text
Intelligence 数据信号
        ↓
内部资格判断与路径选择
        ↓
Moloco 关系审核 / GatherOne 分配
        ↓
客户触达与机会确认
        ↓
SDK 和/或 UA 推进
        ↓
上线或消耗证据与季度复盘
```

## 3. 哪些机会进入 Q3 工作 Pipeline

本项目聚焦具有可信 IAA、SDK、UA 或 Co-win 机会，且尚未被 Moloco 充分覆盖的中国出海移动开发者。

月度 Intelligence Pipeline 结合市场、下载、UA、Moloco 历史、Publisher 和 Supply 背景。候选客户在进入季度执行队列前必须完成审核。

### 优先级与商业路径

- **P1** 机会优先进入关系审核和 Agency 路由；它们具备最强的当前 IAA 或 Hybrid 机会数据信号。
- **P2** 机会在数据支持可信商业路径时进入正常的季度审核队列。
- **P3** 记录仅保留用于观察或补充验证；默认不进入 active P1/P2 执行队列。

对于每个 Qualified Bundle，owner 需要记录一条主要商业路径：

- **IAA-first：** 优先推进 Publisher SDK / IAA 激活。
- **UA-first：** 优先推进 Moloco DSP / 用户获取讨论。
- **Co-win：** 当客户背景支持时，同时推进两条路径。
- **Observe：** 保留至后续审核，而不立即启动 active outreach。

优先级只是审核的起点，不能替代业务判断。关系覆盖、客户适配度、产品组合、可触达性和现有 Moloco 背景都必须在 Bundle 被释放执行前纳入考量。

|---|---|---|
| 项目统筹与数据闭环 | Owen | 负责项目节奏、优先级、Pipeline 质量、跨团队协调、升级和汇报。 |
| Non-Gaming 机会审核 | Daniel | 为 Non-Gaming 潜客提供机会和关系判断输入。 |
| Gaming 机会审核 | Clara | 为 Gaming 潜客提供机会和关系判断输入。 |

| Supply Enablement 与升级 | Owen / Daniel / Morden / Jim / 指定 SME | 提供 Publisher 背景、SDK 指引，以及对重要或复杂问题的支持。 |

该职责边界经过明确设计：Moloco 关系 owner 可以保留客户引荐责任，而 GatherOne 仍负责后续日常执行。只有在接收 owner 明确、下一步已记录时，转交才算完成。

## 5. 端到端工作流程

### 第一步：发现与刷新

Intelligence 按月刷新候选客户数据，并审核新的 P1/P2 信号。审核考虑 Bundle 身份、Publisher 背景、下载规模与趋势、变现信号、活跃 UA 信号、Moloco 历史以及相关 Supply 背景。

GatherOne 也可以提交自有线索。这些线索必须经过相同的 Bundle 级审核，之后才会进入工作 Pipeline。

### 第二步：资格判断与路径选择

Owen 对可能进入当季的候选客户完成内部资格判断，结果仅有四种：

| 结果 | 含义 |
|---|---|
| **Qualified** | 可以进入季度执行队列并开始关系审核。 |
| **Needs Review** | 具备潜力，但仍缺少关键事实或关系判断。 |
| **Hold** | 暂不投入执行资源，保留至后续刷新再审核。 |
| **Exclude** | 不符合项目目标或已被充分覆盖。 |

每个 Qualified Bundle 都必须有优先级、主要商业路径、owner 建议，以及带日期的下一步。

### 第三步：关系审核与执行 owner 分配

Moloco Sales 及相关关系 owner 判断账号是否应保留、引荐或释放给 GatherOne。在开始触达前，必须检查现有 Moloco 或 Supply 覆盖。

GatherOne 接收 Bundle 后，需要分配一名销售 owner 并记录第一个动作。一个 Bundle 不能同时存在两个相互竞争的日常执行 owner。

### 第四步：客户触达与机会确认

GatherOne 主导客户沟通，并记录有实质意义的推进。有效更新应包含触达日期、客户反馈、当前状态和具体下一步。

目标是确认客户是否存在可执行的 IAA/SDK、UA 或 Co-win 机会，而不只是发送一条初始消息。

### 第五步：推进 SDK 和/或 UA 工作

当客户有兴趣时，团队沿相应商业路径继续推进。GatherOne 持续负责客户协作；Moloco 团队提供所需的关系、商务或技术支持。

支持请求必须包含足够的可执行背景：Bundle、平台、集成或商务阶段、问题描述、支持 owner，以及客户 deadline（如适用）。

### 第六步：验证结果并完成闭环

SDK 上线、覆盖率、测试、Publisher 表现和 UA 进展应尽可能通过可追溯的事实记录。已关闭或暂停的机会也必须保留清晰结论，避免下一次审核在没有背景的情况下重复启动相同工作。

## 6. 季度 Tracker 工作规则

季度 Tracker 是 owner、客户进展、下一步、支持请求和结果证据的工作记录。它不替代底层 Intelligence 数据源。

所有 active Bundle 均遵循以下规则：

1. 使用 `quarter + normalized bundle` 作为去重键。
2. 维护一个当前执行 owner。
3. 记录具体下一步和 due date；仅写“跟进”并不充分。
4. 每次出现重要客户动作或结论后更新记录。
5. 月度 Intelligence 数据刷新时保留手工工作流字段：owner、stage、feedback、next action 和 support notes。
6. 对 blocker 记录分类和明确的 support owner。
7. 使用证据、日期或约定的数据口径记录上线和消耗结果。

没有 owner、下一步或近期更新的记录，需要在下一次 Pipeline 会议前审核。超过 14 天没有更新的记录必须明确下一步、回到审核，或做出 Hold/Closed 决定。

## 7. 工具与数据职责

| 工具或数据层 | 在工作流程中的作用 |
|---|---|
| **Intelligence Pipeline** | 产出刷新后的候选信号和资格判断、优先级所需的数据背景。 |
| **Bundle Lookup** | 支持对一个或多个 Bundle 进行重点审核；它辅助决策，但不会自动把客户加入季度队列。 |
| **季度 Tracker** | 记录当季 active 机会的 owner、stage、客户动作、支持需求和已验证结果。 |
| **季度源 Sheet** | 提供当前季度的工作背景，并在季度变化时更新。 |
| **BigQuery facts** | 提供只读源事实，并支持基于证据的上线和消耗结果验证。 |

月度数据刷新可以更新已有 Bundle 的 Intelligence 事实字段，但不能覆盖团队维护的手工执行记录。

## 8. 运行节奏

### 月度 Intelligence 刷新

- 刷新候选客户数据，并审核新的 P1/P2 机会。
- 在新 Bundle 进入 active 季度队列前完成验证。
- 刷新已有 Intelligence 事实，不创建重复记录，也不替换手工执行字段。

### 双周 Pipeline Review

参会者审核 active 机会、缺失 owner、过期更新、支持 blocker 和需要跨团队协调的事项。讨论聚焦于决策和下一步，而不是逐行重读表格。

### 持续支持升级

- 客户关系、引荐和商务协作：Michael 和 Owen。
- 优先级、数据和 Pipeline 问题：Owen、Daniel 和 Clara。
- SDK 集成、mediation 和技术问题：Supply team。
- 对客户上线有实质影响或超过预期响应窗口的问题：由 Owen 与相关 owner 发起升级。

## 9. 如何衡量进展

项目追踪完整的转化路径，而不只追踪潜客名单的大小：

- Qualified P1/P2 Bundles；
- 已接收并已分配执行的 Bundles；
- 有效客户触达和已确认机会；
- 正在推进的 SDK 与 UA 机会；
- 具备上线或消耗证据的 Bundles；以及
- blocker 解决情况和更新质量。

每次审核也应沉淀实际学习：哪些数据信号能识别出最可执行的客户、哪些 handoff 最有效，以及哪些反复出现的客户问题需要通过可复用的 Enablement 解决。

## 1. 导读：ArcReel 怎样使用 ADR

**格式。** 每篇 ADR 是一个 Markdown 文件，文件名是 `四位编号-英文短语`，文件头只有一行 YAML frontmatter `status`；一级标题就是决策本身（整句中文）；正文第一段合写背景与决定，然后是固定小节：`Consequences`（后果），以及 `Considered Options` 或「明确不采用」（被否决的备选）。较新的 ADR 还常有「变更闸门」一句：后续 PR 想推翻这条决定，必须先把本 ADR 标为 deprecated；以及「重构触发点」：写明在什么条件下这条 YAGNI 取舍应被重新评估（例如「出现第三个多 secret 供应商时」）。

**状态与取代。** 88 篇的 `status` 字段**全部**是 `accepted`。取代关系不写在 status 字段里，而是两种写法：①被取代篇目顶部加一段引用块，说明哪几段已被哪篇 ADR 取代、其余仍有效；②取代方在正文里写明「本 ADR 取代 00xx 的某某段」。因此 ArcReel 的取代几乎都是**段落级的部分取代**，没有整篇作废。本章在每条的「状态」里标注这种关系：

| 被部分取代 | 取代方 | 被取代的内容（概括） |
| --- | --- | --- |
| 0005 | 0046 | 会话流由消费方解码哨兵 → 改为 typed 事件流 |
| 0019 | 0086 | 参考生视频路线的兜底分辨率例外被取消 |
| 0033 | 0045、0055 | 广告参考路线的 `shots + reference_units` 派生结构只剩历史意义 |
| 0041 | 0080 | 「脚本规划为持久基底 + 按条目指纹增量」一段；自由文本列「丢失可容忍」的口径 |
| 0049 | 0086 | video lane 的兜底分辨率与时长维度的空值放行 |
| 0064 | 0073 | 「未登记引用只警告不阻断」「无资产图就用原图」两段 |
| 0074 | 0088 | 用户记忆目录位置与数据根前缀约定 |
| 0075 | 0080 | 无脚本规划剧本的依据登记方式 |

**主旋律。** 读完 88 篇，反复出现的设计信念有六条，后面各主题都是它们的具体化：

1. **钱按调用次数花。** 取消、重启、重试、批量准入、产物时效，几乎每一条都在防「重复扣费」或「用户付了钱却拿不到产物」（0006、0007、0047、0061、0062）。
2. **单一真相源，派生物读时计算。** 能力声明在模型级（0013）、时长在 `supported_durations`（0018）、参考图从正文读时派生（0064）、产物时效读时比对而不落状态（0062）、路线只在项目字段（0055）。
3. **执行时解析，不在入队冻结。** capability、尺寸、provider/model 都在 worker 起跑时按最新状态求值；只有真正要付费提交的那一刻才冻结 execution checkpoint（0001、0054、0007）。
4. **fail-loud 优先，唯一的宽容点被圈死。** 「不更坏」只在两个写盘咽喉点存在（0002、0003），其余一律显式报错、禁止「零信号成功」；不允许静默换模型或静默回退（0015、0049、0054）。
5. **昂贵步骤前有人工确认门。** 内容确认后才跑提示词编写（0041/0080），整批准入含跨档费用确认（0061），stale 产物不自动重生（0062）。
6. **YAGNI 但留触发点。** 定型列而非 JSON（0037、0042）、队列自研（0083），都写明何时应重评。

**主题分组**（共 13 组，编号即本章小节）：任务队列与执行恢复（6）｜生成参数解析与执行事实（9）｜Provider / Backend / 注册表（13）｜自定义端点、ComfyUI 与市场（6）｜Agent 运行时与安全（16）｜剧本、分集与内容模式（10）｜视频单元与提示词（3）｜资产与一致性（6）｜产物、版本与迁移（4）｜计费与用量（3）｜数据与存储（3）｜前端、实时与认证（6）｜工程治理与文档（3）。

**Linglong 评估标签。** 【采纳】= 原则与机制都适用；【简化后采纳】= 原则适用，但 Linglong 的单供应商（Vertex）/ 数据库存储 / 无内嵌 Agent 等条件让实现可以大幅简化；【不适用（范围外）】= 依赖 scope lock 排除的能力（小说改编、剪映草稿、非 Vertex 供应商）；【待评估】= 取决于 Linglong 尚未决定的架构选择（主要是是否引入内嵌创作 Agent、多实例部署形态）。

## 2. 任务队列与执行恢复

### ADR-0001 图片 t2i / i2i 能力只在执行时确定
- 路径：`docs/adr/0001-image-capability-resolved-at-execution.md` ｜ 状态：accepted
- 问题：一张分镜走文生图还是图生图取决于执行那一刻是否有参考图（含上一张分镜），批量重生时第 N 张依赖的第 N-1 张在入队时往往还没画出来，入队与认领阶段结构上无法知道答案。
- 决策：capability 只在执行层精确解析，入队不冻结执行身份；入队只按 t2i 派生一个「代表性」provider 写进任务行，仅供认领过滤与限流路由；`image_edit`（必然 i2i）是唯一在入队即精确解析、槽位不可用直接拒绝的例外。
- 原因/取舍：接受「t2i 与 i2i 配了不同 provider 时，限流记账落在错误的池上」这一不影响正确性的近似；明确否决在入队时记 `needs_i2i`——那要把参考图收集逻辑复制进调度层，且批量场景下入队时的答案本来就是错的。
- 对 Linglong：【简化后采纳】Linglong 图像只有一个 Vertex 模型，t2i/i2i 同池，近似问题自然消失；但「执行时读取最新参考集合、入队不冻结」要保留。（P-07）

### ADR-0006 取消只对排队中的任务开放
- 路径：`docs/adr/0006-cancel-only-queued-tasks.md` ｜ 状态：accepted
- 问题：媒体生成按供应商调用次数计费，调用发出后本地中断既省不了钱、又丢掉用户已付费的结果；此前实现过「取消执行中任务」，围绕它长出了中间态、0 行写入协议、产物回滚回执三套易漏的机制。
- 决策：状态机收敛为排队→执行→成功/失败，另加排队→已取消（来源区分用户与级联）；执行中任务拒绝取消（409），项目级「全部取消」只清排队任务；服务关停等在跑任务完成；进程级打断时以 shield 方式落终态，避免变成孤儿。
- 原因/取舍：费用模型相悖、回执要沿每条写路径透传难以测穷尽、真实需求很窄；明确禁止为「停下昂贵生成」重新开放执行中取消，除非先解决供应商侧的取消与退费语义。
- 对 Linglong：【采纳】Veo / Gemini 同样按调用计费、LRO 发出后不退费；取消按钮只对 queued 显示，级联取消下游排队任务。（P-11、P-12）

### ADR-0007 重启后的孤儿任务不重新生成，提交-轮询型按 job_id 续轮询
- 路径：`docs/adr/0007-orphan-tasks-not-requeued-on-restart.md` ｜ 状态：accepted
- 问题：旧逻辑在重启后把所有 running 任务丢回队列重跑，每次重启都重复扣费；曾有真实事故（视频池被长轮询任务占满、若重启就会重复三笔）。
- 决策：孤儿默认标 failed 并写明分类失败码（重启丢失 / 不支持续跑 / 远端已过期）；提交-轮询型视频在 submit 后**同步**持久化 provider job id，持久化失败立即判失败以防「供应商在跑、本地不知道」的幽灵任务；重启时对带 job id 的孤儿调用 backend 的续轮询入口。后续又加入版本化的 execution checkpoint：首次 submit 紧前冻结任务坐标、实际 provider/model、最终 prompt、时长与实际发送的媒体摘要，续跑只按 checkpoint 回放，身份漂移即显式失败；发送给供应商的媒体先物化到任务私有 staging；413 只在能证明供应商未受理时才降档重试；正常路径与续跑共用同一个「临时文件→记账→版本登记→提升为正式文件」事务。图片不做续跑（同步为主、重生便宜）。
- 原因/取舍：费用 = 次数，requeue 会变成「次数 × 重启次数」；该策略以「worker 与 server 同进程」为前提，多 worker 部署时必须重审。
- 对 Linglong：【采纳】Vertex Veo 的 long-running operation name 就是 job id：必须在进入轮询前落库，重启后续轮询而非重新提交；checkpoint 与「幽灵任务」防护应作为 P-11 的验收项。（P-11、P-07、P-12）

### ADR-0010 TTS（audio）走生成队列，但后端保持同步
- 路径：`docs/adr/0010-tts-audio-through-generation-queue.md` ｜ 状态：accepted
- 问题：TTS 后端是同步秒回的一次请求，看起来像文本调用；但它的生成基数（每段一条、可批量、可重生）与图片/视频一致。
- 决策：audio 作为 worker 的第三条 lane 入队，复用任务面板、取消与续传 UI；后端仍是同步调用，无 job id、孤儿直接判失败。核心规则：「是否入队由生成基数决定，不由后端同步与否决定」。
- 原因/取舍：否决「同步内联 + 前端串行批量」——进度绑在浏览器标签页、不可取消、不可跨设备；异步长文本 TTS 作为预留扩展点。
- 对 Linglong：【采纳】旁白/配音统一进任务面板与 P-11 恢复语义；具体 TTS 供应商需在 Vertex/Google 范围内另行确认（待确认）。（P-08、P-11）

### ADR-0061 批量视频生成的准入是整批的，执行结果才是逐条的
- 路径：`docs/adr/0061-batch-video-admission-all-or-nothing.md` ｜ 状态：accepted
- 问题：逐条放行会让先创建的任务已经计费、后面的目标失败，用户拿到半成品且要自己拼原因；Web 与 Agent 各有一份判定时口径必然分叉。
- 决策：创建任何任务前，把目标集合整体评估一次（重规划、资产缺失、TTS 状态、超出供应商上限、在途冲突、未确认的跨档费用等），任一不通过则**零任务**；全部通过后同一次操作建完整任务集。入队中途失败时已建任务照常执行、未建目标逐 ID 报失败（下次「缺失即生成」正好补上）。三种结局（放行 / 待确认 / 受阻）都用 200 同一信封返回；确认只绑定目标集合与选项，不冻结内容快照；不自动重生 stale 产物。判定拆成传输无关的纯折叠 + 接入当前状态的服务层，Web 与 Agent 共用。
- 原因/取舍：否决前端串行逐条入队、否决「首个错误即中断只报一个」、否决把「评估结论为不放行」塌成 4xx、否决确认时冻结快照；跨档费用按档位聚合展示，报价不全时不显示合计以免低报。
- 对 Linglong：【采纳】这是「昂贵步骤前人工确认」在服务端的标准形态，应成为批量生成视频/关键帧的唯一入口。（P-07、P-09、P-11、P-12）

### ADR-0083 生成任务队列现阶段保持自研
- 路径：`docs/adr/0083-generation-queue-stays-in-house-for-now.md` ｜ 状态：accepted
- 问题：是否换用 Celery、dramatiq、arq、taskiq、procrastinate、APScheduler 等库。
- 决策：现阶段不换。候选要么需要应用外的消息服务，要么不能把任务状态放进同一个 SQLite/PostgreSQL 双方言库，APScheduler 4 仍是 pre-release；而真正能被库替掉的通用底层（认领、租约、状态守卫、占用台账）只有几百行，其余容量热重载、孤儿续跑、准入、记账等领域逻辑换库后仍需自写。
- 原因/取舍：写明重评条件——支持多进程/多实例、只需 PostgreSQL、出现稳定的同类库；RPM 限流不属于队列，由调用通道自行节流。
- 对 Linglong：【待评估】ArcReel 的前提（单进程、默认 SQLite、Windows 原生）在 Linglong 的 GCP 部署下多半不成立（多实例待确认），Cloud Tasks 或 PostgreSQL 原生队列可能更合适；但「领域逻辑无论如何自己写、只比较通用底层维护成本」的评估方法可直接借用。（P-11）

## 3. 生成参数解析与执行事实

### ADR-0011 媒体尺寸：比例由 aspect_ratio 唯一决定
- 路径：`docs/adr/0011-aspect-ratio-first-media-size.md` ｜ 状态：accepted
- 问题：各后端用「(档位, 比例) → 像素」静态表或把分辨率值直接当尺寸，只要分辨率值携带比例（错表或用户自填 WxH）就会压过项目比例，产出比例错误的图；排查确认是机制缺陷而非个别 bug。
- 决策：确立产品原则——项目 `aspect_ratio` 是比例唯一真相、永远优先，分辨率只决定清晰度；新建统一尺寸模块按「约简比例 × 短边」算精确尺寸再按后端像素约束夹取；自定义 WxH 只取短边；缺省兜底 720；固定档位的后端（如 Sora）吸附到比例最近的合法档；比例本就是独立字段的后端（Veo 等）不改尺寸逻辑。
- 原因/取舍：否决逐后端修表；接受统一短边档位改变部分后端既有输出；个别有固有约束的后端作为正当例外保留。
- 对 Linglong：【采纳】CTV（16:9）与移动（9:16）并行交付，比例错的产物不可用；Vertex 的比例是独立参数，关键是项目比例在 brief 中唯一定义并贯穿全链路。（P-02、P-07、P-10）

### ADR-0012 参考图压缩：保守通用上限 + 被动 413，只动上传副本
- 路径：`docs/adr/0012-reference-compression-conservative-ceiling.md` ｜ 状态：accepted
- 问题：I2I / I2V / R2V 把多张大图 base64 内嵌后请求体超限失败。
- 决策：在所有生成的汇流点对「发送后即删除的参考副本」主动压缩，源资产与产出保持全质量；使用单一保守的总/单图上限（可按供应商覆盖），被动捕获 413 后降一档重试；统一高质量 JPEG；先降分辨率、后降质量且有质量下限；单张首尾帧只在超字节时重编码、永不缩尺寸。
- 原因/取舍：不硬编码各家未公开且常变的上限；代价是偶发一次被拒的 413（ingress 拒绝不计费）。
- 对 Linglong：【简化后采纳】「只压副本、不动源与产出」「首帧不缩尺寸」直接适用；Vertex 可能更适合用 GCS URI 传参考图避开体积问题（待确认）。（P-07、P-05）

### ADR-0018 视频时长以每模型 supported_durations 为单一真相源
- 路径：`docs/adr/0018-video-duration-supported-durations-single-source.md` ｜ 状态：accepted
- 问题：后端把用户选的 6 秒静默改成 8 秒、以及隐性默认时长列表，导致「选 6 秒被改 8 秒、再被对端判非法」的事故。
- 决策：每个视频模型声明非空离散时长集；剧本 prompt、前端选择器、请求体三处同源消费；请求原值透传、越界由供应商 400 反馈；解析得到空集即 fail loud。例外：个别供应商按端点差异校正；ComfyUI 端点「时长由 workflow 固定」是带独立标志的合法空集。
- 原因/取舍：宁可显式失败引导修配置，也不静默篡改用户或 LLM 的选择；schema 不引入连续区间类型。
- 对 Linglong：【采纳】Veo 各版本合法时长以官方文档为准（不得猜），脚本规划、分镜 UI 与请求体必须读同一份声明。（P-06、P-07）

### ADR-0019 纯清晰度参数未配置时不传
- 路径：`docs/adr/0019-resolution-none-means-omit-param.md` ｜ 状态：accepted（参考路线例外已由 0086 取消）
- 问题：我方按模型硬编码默认分辨率等于替供应商猜默认值，且无法区分「未配置」与「显式选择」。
- 决策：删除我方默认表；分辨率按 项目 → 旧字段 → 自定义模型默认 → 空 解析，空表示调用时不带该参数、交给 SDK 默认。需要承载比例的尺寸不适用（走 0011 永远计算下传）。
- 原因/取舍：把默认权还给 SDK；不设系统级全局默认分辨率。
- 对 Linglong：【采纳】与本仓库 CLAUDE.md「不猜模型参数」一致。（P-07）

### ADR-0049 生成任务的 provider 解析收口为一次性的 GenerationContext
- 路径：`docs/adr/0049-generation-context-single-resolution.md` ｜ 状态：accepted（video lane 兜底部分由 0086 取代）
- 问题：执行层拿到 generator 后又各自二次解析配置，两次之间配置变化会「按 A 造后端、按 B 查分辨率」；视频二次解析失败时静默落到硬编码模型；参考视频任务掏私有属性重建身份；只配了图片供应商的项目会因视频解析失败而整体报错。
- 决策：唯一入口返回不可变 context：一次会话内完成全部声明 lane 的解析与后端构造；lane 需具名声明，未声明访问即报错；能力按「规范 provider 身份 × 后端实际模型」查询，消除意图与实际构造物的错配；解析或构造失败整体上抛、无跨供应商兜底，只有能力元数据查询失败降级放行。
- 原因/取舍：否决把解析产物塞进 MediaGenerator、否决为本地可替换依赖开 Port、否决部分成功、否决保留硬编码兜底（会在用户明确选了某供应商时静默换成无关供应商并计费）。
- 对 Linglong：【简化后采纳】单供应商下实现很薄，但「一次解析、全链路共享、禁止静默换模型」必须保留。（P-07、P-12）

### ADR-0050 图片编辑是图的分叉，不是 prompt 的分叉
- 路径：`docs/adr/0050-image-edit-forks-image-not-prompt.md` ｜ 状态：accepted
- 问题：局部微调时按原 prompt 重画会连满意部分一起推翻；上传替换又要求用户自备编辑工具。
- 决策：新增独立任务类型 `image_edit`：以当前图为唯一参考、用户增量指令为唯一 prompt 调用 i2i，新图覆盖 current、旧图进版本历史并标记来源；不回写原 image_prompt（之后重新生成仍按原 prompt）；执行时读 current；失败时 current 与版本零改动；仅限资产图与分镜图。
- 原因/取舍：否决蒙版/inpaint（供应商支持窄）、否决把指令合并进 prompt（指令脱离当前图即失效）、否决预览确认制（版本历史兜底）、否决服务端同资源互斥（前端占用态负责）。
- 对 Linglong：【采纳】Gemini 图像模型天然支持指令式编辑；这是 P-09「非破坏性修改」的最小实现。（P-09、P-05）

### ADR-0054 图片/视频模型按能力桶配置：单一默认 + 可选覆盖
- 路径：`docs/adr/0054-media-model-capability-buckets.md` ｜ 状态：accepted
- 问题：部分视频模型只有部分能力（仅图生、无参考图槽位），单一「视频模型」配置表达不了，选错要到执行期才失败。
- 决策：图片分 t2i/i2i、视频分 i2v/r2v 覆盖桶，与文本档位同构、项目优先解析；视频先按项目生成路线定轴，参考路线里无参考图的单元降级走 i2v 桶；参考路线的报价、预检、限流与执行共用同一「请求投影」；能力不满足时结构化报错、不换模型；音轨能力按桶各声明一份；两条路线都不在入队时锁定 provider/model，submit 前才落 checkpoint。
- 原因/取舍：否决 t2v 独立桶、否决按路线逐路配模型、否决强制逐桶配置、否决静默换模型、否决写入侧拦截与级联清理（由解析闸统一兜底）。
- 对 Linglong：【简化后采纳】Linglong 视频只有 Veo，桶退化为「一个默认」；但「按路线定能力、不静默换模型、submit 前才冻结身份」保留。（P-07）

### ADR-0056 执行期判据与真实请求同源
- 路径：`docs/adr/0056-execution-predicates-same-source-as-request.md` ｜ 状态：accepted
- 问题：计费口径、成片是否有声、校验放行曾读 ArcReel 侧配置的中间字段推断，而供应商只看请求体，中间隔着归一、回退、截断等变换，导致「请求有声、成片无声、仍按有声价出账」。
- 决策：一切执行期判据取自真正发给供应商的字段，或调用与请求构造同一个变换函数；计费口径与请求口径并列透出、各自取用，不互相兼任。
- 原因/取舍：否决按中间字段推断、否决在判据处复制构造逻辑。
- 对 Linglong：【采纳】报价、扣费记录与「Veo 输出是否含音轨」判断都应从最终请求对象派生。（P-07、P-12）

### ADR-0086 视频请求事实只求值一次
- 路径：`docs/adr/0086-video-request-facts-evaluated-once.md` ｜ 状态：accepted
- 问题：执行模型、下发分辨率、收窄后的可选时长、音轨形态由报价、预检、规划、界面、Agent、执行各自推算，结果分叉（预检确认的秒数 ≠ 执行申请的秒数，报价与扣费各按一个分辨率）。
- 决策：把这些收成「视频请求事实」，按项目 × 路线 × 能力桶 × 身份来源求值一次，各消费方只读；读侧身份取当前配置解析出的模型，执行侧取实际构造的通道，其余求值相同；分辨率未设即不下发（两路线同口径）；i2v 桶不可用时档位如实为「未知」不回退；执行期时长解析失败即阻断（端点固定时长的合法空集除外）。
- 原因/取舍：否决软回退到 r2v 档位、否决保留兜底分辨率、否决读写两侧各自组装、否决界面镜像判定。
- 对 Linglong：【采纳】为 Veo 请求建一个共享的「请求事实」对象，报价/确认/执行/审计同读。（P-07、P-12）

## 4. Provider、Backend 与模型注册表

### ADR-0008 自定义供应商凭证固定为 api_key + base_url
- 路径：`docs/adr/0008-custom-provider-credentials-single-field.md` ｜ 状态：accepted
- 问题：可灵 JWT 双密钥、Vertex 服务账号文件、火山 AKSK 签名等多字段凭证协议是否应开放给用户自建的供应商。
- 决策：自定义供应商凭证模型长期固定为单 key + 入口 URL；多字段协议只能做成内置供应商；用户走中转站时由中转站负责协议翻译；禁止把多个密钥拼进一个字段。
- 原因/取舍：让凭证层、脱敏、表单、发现接口都不被协议形态污染；代价是不可中转的协议（如 Vertex）永远不出现在自定义供应商里。
- 对 Linglong：【不适用（范围外）】Linglong 只用 Vertex、无自定义供应商；可借鉴的只有「凭证形态与协议实现解耦」这一抽象原则。

### ADR-0013 能力声明收敛到模型级
- 路径：`docs/adr/0013-model-level-capability-source-of-truth.md` ｜ 状态：accepted
- 问题：能力声明在供应商顶层时必然与个别模型的真实能力漂移（如某文本模型不支持结构化输出却被顶层声明覆盖）。
- 决策：能力声明在模型条目上，供应商级能力是只读聚合视图；注册表声明是描述性元数据，后端运行时构造出的能力才决定实际参数。
- 原因/取舍：多一次聚合，换来单一真相源；新增模型只写一条声明。
- 对 Linglong：【采纳】即使只有 Vertex，也应按模型（各 Veo 版本、Gemini 图像/文本）声明能力，而不是按「Vertex」一个整体。（P-07）

### ADR-0014 结构化输出：选择性降级
- 路径：`docs/adr/0014-instructor-selective-structured-output-fallback.md` ｜ 状态：accepted
- 问题：并非所有模型/中转都真正支持原生结构化输出，第三方中转甚至会静默忽略 wire 级 schema 参数。
- 决策：原生支持的走原生；两种情况才降级——事前能力门控（未声明支持）与事后复验（HTTP 200 但返回不满足 schema）；降级手段按「是否必须绕开 wire 通道」分化：一类后端用 Instructor，Gemini 后端用 prompt 注入 schema 重发；降级时原生调用的 token 并入统计。
- 原因/取舍：否决全部统一走降级路径（更慢更不准）、否决 PydanticAI / BAML 等更重方案。
- 对 Linglong：【简化后采纳】直连 Vertex 不存在中转忽略 schema 的情况，但「200 之后仍复验 schema、不合即显式处理」值得保留。（P-04）

### ADR-0015 图像端点按能力拆成 T2I / I2I 双槽，不做隐式回退
- 路径：`docs/adr/0015-image-endpoint-split-by-capability-no-fallback.md` ｜ 状态：accepted
- 问题：中转生态里很多模型只有生成接口没有编辑接口，带参考图时被路由到编辑接口后远端 404、归因模糊。
- 决策：端点拆为「通配 / 仅 T2I / 仅 I2I」三条，默认配置按能力分槽；运行时严格按是否携带参考图选择路径，能力不匹配抛带稳定错误码的能力错误；删除「参考图读不到就回退 T2I」之类的隐式回退。
- 原因/取舍：失败前置、错误清晰，胜过自动派发后远端含糊报错。
- 对 Linglong：【简化后采纳】端点拆分不适用；但「参考图读取失败绝不静默降级为文生图」必须采纳——对商品保真是硬要求。（P-07、P-05）

### ADR-0016 供应商多凭证：独立凭证表 + 手动切换活跃凭证
- 路径：`docs/adr/0016-provider-multi-credential-manual-active.md` ｜ 状态：accepted
- 问题：每个供应商需要多套凭证，放在共享 KV 配置里命名脆弱、并发读改写复杂。
- 决策：专用凭证表，每供应商至多一条活跃（部分唯一索引兜底），用户手动切换、全局生效，删活跃时自动改选最早一条；明确不做自动轮换、负载均衡、加密存储与使用统计。
- 原因/取舍：行为可预测优先；切换需触发后端缓存失效。
- 对 Linglong：【不适用（范围外）】Vertex 项目 / location / 凭证属用户所有的部署配置（见 CLAUDE.md），不在产品内做多凭证切换。

### ADR-0037 内置供应商多 secret 用按注册键命名的定型列
- 路径：`docs/adr/0037-builtin-provider-multi-secret-typed-columns.md` ｜ 状态：accepted
- 问题：可灵是首个需要两个 secret 字符串的内置供应商，现有凭证表只有固定三列。
- 决策：凭证表新增两个按注册键命名的可空列，使「注册键名 = 表单字段名 = 后端构造参数名 = 配置键」四者同名；否决拼接字符串、通用 JSON 列、凭证子表、复用 KV。
- 原因/取舍：YAGNI——只有一家需要；接受稀疏列；重构触发点是出现第三个多 secret 供应商。
- 对 Linglong：【不适用（范围外）】国内供应商专用；可借鉴的是「字段集稳定时用定型列、并写明重构触发点」这一取舍方法。

### ADR-0038 注册表键与发给供应商的模型名解耦
- 路径：`docs/adr/0038-registry-key-decoupled-from-api-model-name.md` ｜ 状态：accepted
- 问题：注册表以模型名字符串为唯一键，同时兼任 UI/持久化标识、计费能力查表键与发给供应商的 API 名；可灵 v3-omni 的图像与视频在 API 上同名，单键容不下。
- 决策：模型条目增加可选的「API 模型名」字段（默认回退键名），图像条目用别名键；明确不改成 (模型, 媒体类型) 复合键——那会把代价推到前端选择、项目文件、调用记录、定价快照等所有只带裸字符串的边界。
- 原因/取舍：只解耦冲突的那一职；接受一个供应商世界里不存在的合成键；两栖模型增多时再重评。
- 对 Linglong：【待评估】Gemini 系列是否存在同名跨模态模型（待确认）；可以预留「内部键 ≠ 供应商模型名」，但模型 ID 本身是用户所有配置，不得猜测改动。（P-07）

### ADR-0039 内置供应商后端构造收口为声明式表
- 路径：`docs/adr/0039-builtin-backend-construction-declarative-seam.md` ｜ 状态：accepted
- 问题：内置供应商后端构造在四处命令式分支里各写一遍，供应商知识泄漏到调用方；两份「供应商→后端」映射已漂移；而自定义侧早已是声明式表。
- 决策：新建统一装配入口，按是否自定义分流到两族适配器；内置侧建 (供应商, 媒体类型) → 规格表，每条挂一个构造闭包；构造拆成异步装载（读 DB 与配置，产出配置信封）与同步构造（纯闭包，可脱离 DB 单测）；缓存留在调用方。
- 原因/取舍：否决两表合并（凭证模型本质不同）、否决统一请求值对象（没有第二个消费者）、否决纯数据规格（需要闭包逃生口）、否决「缺席即默认」（打错 id 会静默造出后端）。
- 对 Linglong：【简化后采纳】单供应商下一张小表即可；「构造核心可脱离 DB 单测」「未登记即报错」两点可直接采用。（P-07）

### ADR-0042 自定义供应商并发上限用按 lane 命名的定型列
- 路径：`docs/adr/0042-custom-provider-concurrency-typed-columns.md` ｜ 状态：accepted
- 问题：内置供应商可按 image/video/audio lane 设并发，自定义供应商只能套全局默认，不对称。
- 决策：自定义供应商表加三个按 lane 命名的可空整数列，空即回退全局默认（两层回退，比内置少「供应商声明默认」一层）；否决 JSON、KV、子表。
- 原因/取舍：字段集稳定，与 0037 同构；per-model 并发或动态 lane 出现时再重构。
- 对 Linglong：【不适用（范围外）】无自定义供应商；但「按 lane 设并发上限、空值回退默认」可用于 Vertex 配额保护（实现另行设计）。（P-11）

### ADR-0043 并发上限禁止用户输入 0，0 仅作内部「不支持该 lane」哨兵
- 路径：`docs/adr/0043-forbid-zero-user-concurrency-keep-internal-sentinel.md` ｜ 状态：accepted
- 问题：0 同时是内部「该供应商不支持此媒体」的哨兵和用户可填的值；用户误填 0 会静默关死 lane，之后每个任务报一个答非所问的错误。
- 决策：所有用户输入层与 DB 约束统一要求 ≥1，留空表示回退默认；0 只保留给内部；因前一迁移未发布，直接就地改写该迁移。
- 原因/取舍：否决把 0 立为「禁用 lane」一等公民（真需要应另设显式开关与诚实的失败码）；「未发布迁移可就地改写」是有意取舍，发布后不可再用。
- 对 Linglong：【采纳】小而通用的配置规则：一个值不兼两义，任何并发/配额设置都这样校验。（P-11）

### ADR-0044 文本输出 token 上限是非约束安全阀，结构化截断是硬错误
- 路径：`docs/adr/0044-text-output-token-nonbinding-ceiling.md` ｜ 状态：accepted
- 问题：规划、剧本生成等处把最大输出 token 当成「省钱预算」压低，正常输出被截断，结构化路径抛出不可诊断的异常。
- 决策：统一为一个共享的高位常量，只防模型失控；带 schema 的调用被截断时抛专门的截断错误（点名当前文本模型、建议换输出能力更强的模型），并短路重试循环；自由文本截断维持只记日志。
- 原因/取舍：否决传空交给供应商默认（默认不统一且可能很低）、否决截断后自动缩窗口重试（隐式降级）、否决维护每模型输出上限表。
- 对 Linglong：【采纳】Gemini 生成脚本/分镜结构化 JSON 被截断时，应给出可操作的硬错误，而非静默缩小批量。（P-04、P-11）

### ADR-0047 文本后端重试只包单次网络调用
- 路径：`docs/adr/0047-text-backend-retry-wraps-single-call-only.md` ｜ 状态：accepted
- 问题：整个 generate 被重试装饰器包住、降级在重试范围内，导致降级的瞬态失败会重放已成功（已计费）的原生调用，且异常消息里的模型文本可能误中「429/timeout」等字符串模式。
- 决策：generate 变为无装饰的编排层；重试装饰只出现在单次网络调用方法上；降级路径自带一层同配置重试；schema 不兼容用「空信号」而非异常传出，避免被误判为瞬态错误。
- 原因/取舍：最坏调用次数从几何叠乘变为线性有界；残余风险是库内校验异常消息仍可能触发降级自身重放。
- 对 Linglong：【采纳】所有 Vertex 调用（文本、图像、视频提交）重试边界都应只包单次请求。（P-11、P-12）

### ADR-0051 文本后端按任务档位配置：简单 / 复杂两档
- 路径：`docs/adr/0051-text-backend-capability-tiers.md` ｜ 状态：accepted
- 问题：文本调用点持续增加，一个调用点一个设置项会让配置面线性膨胀，新调用点往往落在设置之外成为不可见的模型来源。
- 决策：每个调用点在代码里固定归属简单或复杂档；用户只配每档模型 + 一个默认；项目优先解析；简单档包含风格图分析，须支持视觉输入，否则报错。
- 原因/取舍：否决按任务逐键配置、否决三档、否决档位同时映射 Agent 模型、否决「维度优先」的解析顺序（会让项目默认形同虚设）。
- 对 Linglong：【简化后采纳】Linglong 文本模型固定为 CLAUDE.md 所列 Gemini 文本模型，档位映射可在代码里预留，但不开放用户改模型。（P-04）

## 5. 自定义端点、ComfyUI 与市场

### ADR-0067 自定义调用端点采用声明式定义
- 路径：`docs/adr/0067-custom-endpoint-declarative-definition.md` ｜ 状态：accepted
- 问题：接入一种新视频协议只能改源码，而长尾聚合站/中转站同属「JSON 进出 + 提交后轮询」流派，只是字段名与取值路径不同。
- 决策：端点定义为带版本号的 JSON 容器：请求用结构模板加占位符与少量固定构造，响应用受限 JSONPath 优先级数组，状态映射为纯字典；定位只覆盖这一流派，并反向把能整体表达的内置 HTTP 后端收编为随版声明式定义；签名鉴权、multipart、SDK 式接入等留在 Python。存储上定义整份存一列 JSON（字段集不稳定），被模型行引用时拒删并返回引用清单。
- 原因/取舍：否决按「覆盖全部协议」衡量而弃用、否决运行时 Python 插件、否决为不可表达构造扩格式。
- 对 Linglong：【不适用（范围外）】Linglong 锁定 Vertex，不做第三方协议接入。

### ADR-0068 自定义供应商端点不限 URL scheme
- 路径：`docs/adr/0068-custom-endpoint-scheme-not-restricted.md` ｜ 状态：accepted
- 问题：自建服务、局域网中转、本机网关常用 http。
- 决策：http 与 https 一律接受，明文风险由用户自担；全产品各路径同口径，不在单一入口设闸；跨源重定向一律卸掉凭证，产物地址只在同源时附凭证。
- 原因/取舍：避免「模型发现能过、真跑视频被拒」的入口分裂。
- 对 Linglong：【不适用（范围外）】无自定义端点；「跨源重定向剥离凭证」若将来下载外部素材可作为安全参考。

### ADR-0078 市场采用多市场源 GitHub 仓库，零服务端、零账号
- 路径：`docs/adr/0078-market-multi-source-github-repos-zero-server.md` ｜ 状态：accepted
- 问题：端点定义的分享只有文件导入导出，中心化市场需要长期运营服务与账号。
- 决策：每个市场源是一个 GitHub 仓库或 https 直链，官方源随版预置、可禁用不可删、同时是模板仓；投稿走 PR + CI 校验；抓取只经 raw 地址（便于统一代理前缀）；索引由 CI 从定义派生、bot 提交；校验器只在主仓实现一份，市场仓 CI 跟随主仓。
- 原因/取舍：否决中心服务、实例内分享、安装量与评分统计、远程禁用；后端代抓任意 URL 须按 SSRF 暴露面设边界。
- 对 Linglong：【不适用（范围外）】内部产品无公共市场需求。

### ADR-0079 市场安装记录是独立实体，已安装端点可原地编辑
- 路径：`docs/adr/0079-market-installation-separate-entity-editable.md` ｜ 状态：accepted
- 问题：从市场安装的端点需要记住来源，但端点表的不变式是「除定义外都是派生镜像」。
- 决策：安装记录单独成表、与端点一对一，记来源键、条目、版本与定义摘要；已安装端点可原地编辑，摘要不一致即标「已修改」，更新前警告；「可更新」只比较版本号；安装是服务端单事务。
- 原因/取舍：内置端点「只读 + 复制」模式不沿用；同版本改内容不判可更新是有意的。
- 对 Linglong：【不适用（范围外）】同上。

### ADR-0081 ComfyUI 端点：一份 workflow 作为自定义端点的第二种 kind
- 路径：`docs/adr/0081-comfyui-endpoint-as-second-custom-endpoint-kind.md` ｜ 状态：accepted
- 问题：用户自建 ComfyUI 的请求体是整张节点图、素材走 multipart、产物是二进制，既装不进内置模型列表，也超出声明式端点的流派边界。
- 决策：一份 workflow + 节点绑定 = 一个 ComfyUI 端点，一台 ComfyUI 服务 = 一个自定义供应商；复用端点的 CRUD、导入导出、拒删、测试与市场载荷；首次引入端点与供应商协议的双向绑定校验；鉴权头模板放端点定义；无供应商账单，费用沿用单价字段、执行时长只记录；取消或超时时 best-effort 通知 ComfyUI 停止以释放显卡（全仓唯一通知供应商的取消）。
- 原因/取舍：否决新增内置供应商、否决扩声明式格式、否决另起实体族、否决一份 workflow = 一个模型行。
- 对 Linglong：【待评估】LinglongLab 另有 ComfyUI 画布与工作流引擎计划，但 Linglong Production 的 scope lock 限定 Vertex Gemini/Veo；若将来 Linglong 引入自有 GPU 通道，再参考本篇与 0082。

### ADR-0082 节点绑定是 ComfyUI 端点的唯一真相
- 路径：`docs/adr/0082-node-bindings-are-the-only-truth-of-comfyui-endpoint.md` ｜ 状态：accepted
- 问题：ComfyUI workflow 没有官方参数化约定，哪个节点接提示词、首帧、尺寸、产物全靠推断；生态做法是每次提交现推。
- 决策：导入时多信号打分推断候选，用户在绑定编辑器确认后落盘，运行时只读绑定；每项三态（已绑定/显式不支持/未推断），歧义与关键项未绑定不可保存；能力只从绑定推导、不单独存储、关闭用户覆盖；该通道把负向段拆为负向提示词参数；尺寸与时长沿用比例优先与帧数换算，未绑定则对应选择器禁用；时长由端点固定时拒绝 TTS 旁白交付并给专门问题码。
- 原因/取舍：否决每次现推（不可复现）、否决要求安装专用节点、否决在绑定外再存能力声明。
- 对 Linglong：【待评估】同 0081；其中「推断只产出候选、用户确认后才成为真相」「能力不存第二份」对任何可配置管线都有参考价值。

## 6. Agent 运行时与安全

> 说明：Linglong 当前后端未使用 Claude Agent SDK 或内嵌对话式创作 Agent（`apps/api/app/ai_video` 中未见相关依赖）。本组多数条目取决于 Linglong 是否会引入内嵌 Agent，因此多标【待评估】；与 Agent 无关、可推广到任意写入面的原则单独标出。

### ADR-0003 Agent 修改项目 JSON 收归服务端工具，裸写一律拒绝
- 路径：`docs/adr/0003-agent-project-json-edits-via-tools.md` ｜ 状态：accepted
- 问题：Agent 能用 Write/Edit/Bash 直接改剧本与项目文件，只过 JSON 语法检查，结构错误照样落盘，让「单一写入守卫点」形同虚设。
- 决策：Agent 对剧本与项目数据的一切写入经服务端进程内工具：先读正文与 canonical revision，再提交「基准 revision + 有序操作批（更新/插入/删除/拆分）」；服务在项目锁内复核 revision、在内存候选上应用全批、统一预检，任一失败返回稳定错误码与定位、整批零写入；插入/拆分发新 ID 且不重排；编辑不删除媒体、不改已生成资产。强制双层：内核沙箱对 Bash 子进程拒写这两类路径，应用层 hook 拒绝内置 Write/Edit。另外把「不更坏」严格限定在两个咽喉点，咽喉外一律 fail-loud，禁止零信号成功；Agent 字段白名单被丢弃时显式反馈；编辑按数据形状路由、生成按项目路线路由。
- 原因/取舍：让 0002 的结构校验真正只有一个强制点；fail-loud 改造前先枚举「读/写 × 键缺失/键脏 × 校验/不校验」矩阵。
- 对 Linglong：【简化后采纳】即使没有 Agent，「OCC revision + 有序操作批 + 整批预检零写入 + 稳定错误码」也应是脚本/分镜编辑 API 的形态。（P-04、P-06）

### ADR-0017 Agent 的 Anthropic 凭证独立存储，按会话注入
- 路径：`docs/adr/0017-agent-anthropic-credential-injected-per-session.md` ｜ 状态：accepted
- 问题：全局环境变量是进程级单值，与多凭证、每会话不同活跃凭证冲突。
- 决策：Agent 网关凭证独立成表、不参与媒体生成；每次新建会话时从 DB 读活跃凭证构造 env 字典注入 SDK 选项，不写进程环境；切换只影响新会话。
- 原因/取舍：已运行会话持有旧 env，只做提示不强制终止。
- 对 Linglong：【待评估】仅当引入 Claude 系内嵌 Agent 时相关；Linglong 当前 LLM 为 Gemini。

### ADR-0025 内核沙箱不可用时服务启动硬失败
- 路径：`docs/adr/0025-sandbox-unavailable-startup-hard-fail.md` ｜ 状态：accepted
- 问题：Agent 工具的安全底座是内核沙箱，探测失败后静默降级会让防线无声消失。
- 决策：启动期检查沙箱依赖，缺失或试跑失败直接拒绝启动（fail-closed）；只有原生无沙箱的 Windows 例外，改用命令前缀白名单。
- 原因/取舍：宁可拒绝服务，也不在无沙箱状态下运行 Agent；生产仍推荐容器。
- 对 Linglong：【待评估】只有 Agent 能执行 shell 时才需要；「安全前提不满足即启动失败」这一 fail-closed 原则通用。

### ADR-0026 Agent 文件防护双层：沙箱管 Bash，hook 管内置文件工具
- 路径：`docs/adr/0026-agent-file-guard-two-layers.md` ｜ 状态：accepted
- 问题：内核沙箱只约束 Bash 及其子进程，SDK 内置的读写/检索工具在主进程执行、不受沙箱约束。
- 决策：内置文件工具用应用层前置 hook 补第二层（敏感文件、跨项目、代码扩展名、越出工作目录），两层共享同一套路径规则；拦截点必须是前置 hook，因为部分读工具会被 allow 规则先放行、到不了权限回调。
- 原因/取舍：评审文件访问改动时必须两层分别确认。
- 对 Linglong：【待评估】同上。

### ADR-0027 供应商密钥禁入进程环境
- 路径：`docs/adr/0027-provider-secrets-banned-from-process-env.md` ｜ 状态：accepted
- 问题：密钥进 `os.environ` 会被 Agent 子进程整体继承，泄漏面大。
- 决策：三层强制——启动时发现进程环境含任何供应商真密钥即拒绝启动；Agent 子进程 env 中其余供应商变量覆盖为空；Bash 命令被 hook 包装为先 unset 固定清单与命名模式匹配的敏感变量再执行；Windows 回退下改由白名单三道规则裁决。
- 原因/取舍：以环境变量配 key 的部署会无法启动，这是刻意的；新增供应商必须登记变量名。
- 对 Linglong：【待评估】Linglong 在 GCP 上用 ADC / Secret Manager（待确认）；若引入可执行命令的 Agent，「子进程不继承凭证」必须照做。

### ADR-0028 SessionActor：每会话单个 asyncio task 串行化 SDK 调用
- 路径：`docs/adr/0028-session-actor-single-task-serialization.md` ｜ 状态：accepted
- 问题：SDK 客户端不能并发调用，且内部基于 anyio，跨 task 持锁易死锁。
- 决策：每会话一个常驻 actor task 独占客户端，查询/中断/断开都经命令队列在 actor 内串行执行，流式接收时与命令队列交错以便及时中断；否决调用方各自加锁与直接并发。
- 原因/取舍：新增 SDK 操作必须走命令队列。
- 对 Linglong：【待评估】引入 Agent 时的并发模型参考。

### ADR-0029 SDK transcript 镜像入自有 DB，闲置会话可驱逐可恢复
- 路径：`docs/adr/0029-sdk-transcript-mirrored-to-db.md` ｜ 状态：accepted
- 问题：SDK 自带的 transcript 绑定本机文件系统，与统一 DB（多用户/PostgreSQL）部署不匹配。
- 决策：自定义存储把 transcript 逐条写 DB（默认逐条立即落盘），启动时迁移本地历史；闲置会话延迟后从内存驱逐，再访问时按会话 ID 用 SDK resume 重建；transcript 只服务 resume，UI 读事件日志（0048）。
- 原因/取舍：接受写放大换崩溃后不丢上下文。
- 对 Linglong：【待评估】多实例部署时尤为必要。

### ADR-0030 会话在首条消息发送时才创建，对外身份统一为 SDK session id
- 路径：`docs/adr/0030-session-lazy-create-sdk-session-id.md` ｜ 状态：accepted
- 问题：预建会话行要自造 ID 再维护映射，并产生从未发言的孤儿行。
- 决策：新会话先以临时内存 ID 启动并发送首条消息，SDK 初始化消息返回真实 ID 后才写 DB，并把内存键替换为真实 ID；此后一律以 SDK session id 为唯一身份。
- 原因/取舍：初始化返回前会话不可寻址；键替换是敏感窗口。
- 对 Linglong：【待评估】同上。

### ADR-0046 SessionManager 拆解边界
- 路径：`docs/adr/0046-session-manager-decomposition-boundaries.md` ｜ 状态：accepted（同时修订 0005）
- 问题：约 2900 行的会话管理器混装访问规则、SDK 选项装配、订阅广播、token/费用抽取、生命周期、序列化六种职责，哨兵泄漏给消费方，规则只能 monkeypatch 测试。
- 决策：析出「Agent 访问策略」单一类（同一规则投影成沙箱配置与 hook 裁决，零 I/O，Windows 降级用布尔参数）、允许 I/O 的选项装配器（负责凭证注入）、typed 事件流（回放 → 直播 → 心跳 → 溢出即流终）、统一订阅广播组件；token/费用与序列化成纯函数；生命周期与驱逐留在核心；actor 不动。
- 原因/取舍：否决按平台拆 adapter（两边各半数空操作）、否决纯函数集（参数爆炸）、否决广播组件包含开场白、否决两段式流接口（会漏消息）、否决把凭证注入并入访问策略（按依赖形状而非主题归类）。
- 对 Linglong：【待评估】其方法论「按依赖形状（有无 I/O）划模块边界」通用。

### ADR-0048 会话事件日志是 UI 时间线唯一读源
- 路径：`docs/adr/0048-session-event-log-single-ui-read-source.md` ｜ 状态：accepted
- 问题：对话 UI 的真相分散在 transcript、内存缓冲、流式预览，没有共享消息身份，只能靠内容比对缝合，丢失与重复持续渗漏。
- 决策：新增每会话单调序号的持久化事件日志：语义在写入点一次定型；用户消息由服务端先落日志分配身份再回显；SSE 以序号为事件 id 支持断点续传；turn 组装是前端纯函数；流式预览只在服务端内存、完成时被同 ID 条目替换；子 Agent 消息全量收录并按父工具调用归组；日志是 transcript 的物化视图，漂移靠重建修复。
- 原因/取舍：否决只收敛去重、否决直接用 transcript 作 UI 日志、否决新旧协议双轨；两表并存是有意双写。
- 对 Linglong：【待评估】若 Linglong 有 Agent 对话或长任务活动流，「服务端分配身份 + 单调序号 + 写入点定型」是通用做法。（P-03）

### ADR-0052 Agent 故障观测保留证据，不推断根因
- 路径：`docs/adr/0052-agent-failure-observations-preserve-evidence.md` ｜ 状态：accepted
- 问题：启动错误因空消息丢失异常类型；SDK 合成的轮次错误被渲染成 Agent 回答。
- 决策：启动失败与轮次失败共用「最小外壳（阶段、时间、项目、会话）+ 脱敏原始载荷」契约；轮次失败在事件日志写入点定型为系统故障事件；只遮蔽可冒用身份或扣费的秘密，其余异常链、堆栈原样保留；界面两层卡片，默认层明确「观测事实 ≠ 根因」，只提供复制、打开设置、重试启动等与根因无关的动作；不自动重放失败轮次。
- 原因/取舍：否决按文案归类根因、否决穷举上游错误映射或塌成「未知错误」、否决自动重放（会重复已执行的工具操作）。
- 对 Linglong：【采纳】适用于任何 Vertex 失败的呈现：展示观测到的状态与原始（脱敏）载荷，不编造原因，不自动重放已计费操作。（P-11）

### ADR-0058 消息改写由应用层前缀分叉实现
- 路径：`docs/adr/0058-session-branch-prefix-fork.md` ｜ 状态：accepted
- 问题：「回到某条历史用户消息重新发出」需要中间点分叉；SDK 原生分叉会丢子 Agent 时间线并重新分配消息 ID，文件回退也不回退对话。
- 决策：把改写点之前的 transcript 前缀（含子路径）从 DB 复制到新会话 ID 下并以 resume 启动；分叉点固定在用户消息边界；条目 ID 原样复制；锚点身份解析集中一处；发布非原子，靠补偿撤回；原会话标记被取代但数据保留，分叉血统另存。
- 原因/取舍：否决 SDK 原生分叉、否决原地截断（破坏 append-only）、否决等上游实现；改写不回退文件与项目数据副作用。
- 对 Linglong：【待评估】仅在有对话式 Agent 时相关。

### ADR-0065 远程 MCP 直接信任现有 API Key
- 路径：`docs/adr/0065-remote-mcp-trusts-existing-api-keys.md` ｜ 状态：accepted
- 问题：对外暴露 MCP 时是否需要细粒度授权。
- 决策：远程 MCP 只接受现有 API Key（即使 WebUI 关认证也不接受匿名），Key 代表完全受信的自动化主体，不做项目白名单、scope、配额；工具清单排除供应商/凭证配置与删除项目，但这是能力边界不是安全边界；审核与费用确认沿用内置 Agent 的交互，不校验额外人类凭据。
- 原因/取舍：单用户产品前提；细粒度权限另议。
- 对 Linglong：【待评估】Moloco 内部多用户环境下「Key = 全权」大概率不可接受，若对外开放工具需另做权限设计。（P-12）

### ADR-0069 内嵌 Agent 以短期 JWT 和开放网络调用同源 HTTP API
- 路径：`docs/adr/0069-embedded-agent-http-api-access.md` ｜ 状态：accepted
- 问题：自定义端点适配需要 Agent 读任意供应商文档并调用已有的校验、测试、保存 API，固定域名白名单覆盖不了。
- 决策：沙箱网络改为放行全部域名并允许本地回环，加入网页抓取工具；每会话签发 15 分钟会话 JWT 与 API 基址注入环境；文件围栏与其他密钥剥离不变。
- 原因/取舍：明确承认两方面扩大信任边界——文档中的 prompt injection 可在有效期内外传 token 并调用全部 API，本地回环暴露整台宿主；JWT 无法提前吊销；「计费与覆盖前回问」只是行为约束不是隔离。
- 对 Linglong：【待评估】此安全姿态不适合直接照搬到 Moloco 内部环境，引入类似能力须经安全评审。

### ADR-0074 Agent 记忆两级落盘
- 路径：`docs/adr/0074-agent-memory-two-level-storage.md` ｜ 状态：accepted（目录位置部分由 0088 取代）
- 问题：Agent 记忆分项目级与用户级，但原生 auto memory 一个会话只认一个目录。
- 决策：原生 auto memory 按会话重定向到项目内部状态目录承载项目记忆；用户记忆自建在数据根下，会话装配时注入其索引；重定向经 SDK 的 flag settings 注入，不物化配置文件；记忆目录不放进会被 profile 重置清空的目录。
- 原因/取舍：否决反向分配、否决两级都自建、否决物化 settings 文件、否决切换配置目录。
- 对 Linglong：【待评估】同上。

### ADR-0087 Agent 工具集单源声明，宿主差异只允许两轴
- 路径：`docs/adr/0087-agent-toolset-single-declaration.md` ｜ 状态：accepted
- 问题：内嵌 Agent 与外部 Agent（MCP）各写一份工具声明，一个月内就出现错误码被改写、同一工具两个 domain key、迁移拒绝三种形状、漏声明迁移阻断。
- 决策：每个工具只有一份宿主无关声明（名称、完整描述、由请求模型派生的 schema、必填的迁移阻断策略、domain key、handler），两个宿主各有薄 adapter；允许的差异只有「项目如何确定」与「长任务是否等待结果」两轴；同一结果对象在两宿主编码出相同 JSON。
- 原因/取舍：否决按宿主取长补短、否决手写阻断集合。
- 对 Linglong：【待评估】若 Linglong 同时向 UI、内部 Agent、外部工具暴露同一能力，这条是防漂移的关键约束。

## 7. 剧本、分集与内容模式

### ADR-0002 剧本保存校验采用「不更坏」语义，资产回写热路径豁免
- 路径：`docs/adr/0002-save-validation-no-worse-semantics.md` ｜ 状态：accepted
- 问题：结构校验只在归档边界调用，写盘路径完全不校验，脏数据到 worker 深处才炸。
- 决策：把结构校验前移到统一写盘入口，但只在「改前合法且改后非法」时拒绝（本次编辑引入新错误），遗留非法剧本照常放行；高频的资产回写路径完全跳过校验；校验对象是结构模型，而非会读磁盘、拒绝半成品草稿的文件系统校验器。
- 原因/取舍：守卫职责是「不让本次编辑带入脏数据」而非为 schema 演进背锅；明确禁止收紧成永远严格。
- 对 Linglong：【采纳】脚本/分镜结构随 Linglong 演进必然变化，「不更坏」+ 写时暴露错误是 P-04 可编辑性的前提。（P-04、P-06）

### ADR-0031 分集以 project.json 账本为单一真相源
- 路径：`docs/adr/0031-episode-ledger-single-source-of-truth.md` ｜ 状态：accepted
- 问题：旧拆分流程以物理集文件存在与否为真相，没有「第 N 集对应原文哪一段」的记录，进度指针文件损坏即不可恢复。
- 决策：分集真相并入项目文件的集条目（原文范围、钩子、drama 分集大纲、咨询性的消费状态），顶层加规划游标与源文件指纹；物理集文件降为同锁派生物；重置波及已消费集时标 stale 不删除。
- 原因/取舍：否决维持物理文件真相、否决独立账本文件或 DB 表、否决下游直读源文、否决消费时按需派生。
- 对 Linglong：【不适用（范围外）】本篇服务于小说分集；「派生文件与账本同锁重写、失效是标记而非删除」的原则在 P-04 仍可参考。

### ADR-0032 分集规划由服务端工具分批滚动执行
- 路径：`docs/adr/0032-episode-planning-server-side-batched.md` ｜ 状态：accepted
- 问题：旧流程由主 Agent 多步执行机械脚本切分，切分点无剧情语义、留不住钩子，逐集滚动看不到下一集。
- 决策：新增服务端规划工具：读数万字窗口调文本模型，一次规划窗口内所有剧情弧完整的集，游标只推进到最后一个高置信切分点；schema 强约束 + 锚点与连续性机械校验，失败带原因重试；drama 账本加厚为分集大纲；审阅为批级，调整走「重置到最早受影响集 + 重新规划」。
- 原因/取舍：否决规划子 Agent、否决全本一次规划、否决逐集拆分、否决 drama 一步直出剧本。
- 对 Linglong：【不适用（范围外）】小说到分集的改编被 scope lock 排除。

### ADR-0033 广告/短片为第三内容类型，骨架按生成路线派生
- 路径：`docs/adr/0033-ad-third-content-mode-unified-skeleton.md` ｜ 状态：accepted（骨架部分由 0045、0055 取代）
- 问题：带货短视频产出单个视频而非多集系列，需要进入类型系统。
- 决策：`ad` 成为内容模式第三值，复用按内容模式分派的全部机制；分镜路线用平铺镜头数组（每镜含段落标记与一等口播文案），参考路线用自包含视频单元；ad 只开放分镜与参考两条路线（宫格与商品高保真冲突）；恒为单集承载，前端隐藏集语义，未来「一产品多变体」以一集一变体扩展；时长约束按路线动态注入。
- 原因/取舍：初版的「镜头 + 引用分组索引」双层结构已由迁移一次性转换并废弃。
- 对 Linglong：【采纳】商业广告是 Linglong 主场景：单集承载、分镜/参考两路线、禁宫格、「一集一变体」的扩展路径都可直接借鉴。（P-02、P-04、P-06）

### ADR-0036 剧本源（screenplay）：提取优先复用全链路
- 路径：`docs/adr/0036-screenplay-source-kind-extract-first.md` ｜ 状态：accepted
- 问题：用户上传自带分集、台词、画外音的成品剧本时，现有「改编式」链路会重切分集、改写台词、丢画外音。
- 决策：新增创建即锁定的第三轴「源文件性质」（小说 / 剧本）；剧本源下整条链路从「创作」翻为「提取优先」，铺在现有每个阶段而非另造解析器；分集永不机械切；逐字保真只锚「可听见的内容」（台词与画外音文字），舞台提示与排版由模型裁量；泛指群演不注册为角色。
- 原因/取舍：否决一把专用大解析器（与按集惰性消费相悖，对野格式脆弱）。
- 对 Linglong：【简化后采纳】「由用户提供剧本的原创短剧」在 scope 内：可听内容逐字保真、提取优先的原则直接适用；小说源分支不实现。（P-04、P-08）

### ADR-0040 drama 口播内容统一为有序 utterances
- 路径：`docs/adr/0040-drama-utterances-ordered-spoken-content.md` ｜ 状态：accepted
- 问题：台词与画外音分在两个无序字段，字幕无源、跨类型先后丢失、说话量与时长脱钩。
- 决策：场景级有序判别联合列表，每条区分「角色台词 / 画外音」、说话人、文本，插入顺序即时序，类型决定下游路由（台词交视频模型生成口型音轨，画外音留给字幕与 TTS）；加场景级原文摘录作追溯锚；字幕从这一序列派生；说话量对时长只做单向约束（只把时长顶上去、永不压下来，保存期只 warn）；旧数据读时迁移。
- 原因/取舍：否决保留双字段仅加排序、否决用「说话人是否为空」隐式判别。
- 对 Linglong：【采纳】短剧与广告口播都需要「有序口播 → 字幕/TTS/时长估算」这一统一地基；其中剪映字幕导出部分不适用。（P-04、P-08）

### ADR-0041 剧本两段式切成「内容 / 视觉」，中间加阻塞式审核门
- 路径：`docs/adr/0041-script-pipeline-script-plan-prompt-authoring-review-gate.md` ｜ 状态：accepted（持久基底与条目指纹部分由 0080 取代）
- 问题：口播与原文内容要穿过「结构→自由文本→结构」两道 LLM 转写，造成保真丢失与创作漂移；且中间态在 Web 端不可见、不可审。
- 决策：脚本规划（script_plan）只负责内容（边界、角色/场景/道具、口播、原文），提示词编写（prompt_authoring）只负责视觉层并对内容**透传**；两段之间加阻塞式 Web 审核门，用户确认后才跑昂贵的视觉生成；透传靠工程保证——视觉阶段的 LLM 输出 schema 只含对齐锚与视觉字段，后端按 ID 合并并校验唯一与全覆盖；参考路线按「单元数一致 + 逐位配对 + 台词逐字 diff」保证。
- 原因/取舍：否决只对剧本源结构化、否决事后检测失真、否决旁观式审核（仍可能错过）。
- 对 Linglong：【采纳】「内容确认门」正是 P-04 与人工确认要求的核心；「LLM 输出 schema 只含它该改的字段」是防漂移的关键工程手段。（P-04、P-06、P-09）

### ADR-0045 剧本骨架注册表以骨架种类为键，轴交互收口进规范/取证双解析器
- 路径：`docs/adr/0045-script-skeleton-registry-dual-resolvers.md` ｜ 状态：accepted
- 问题：骨架表只按内容模式单轴、只覆盖三种骨架，约 19 个文件手写字面量分支并有「非 A 即 B」二值兜底，已导致广告与参考视频项目的分镜级事件从不发出。
- 决策：零依赖叶子模块持有以四种骨架种类为键的窄表；「(内容模式, 生成路线) → 骨架」的规范解析供只持项目配置的消费方，「剧本数据 → 骨架」的取证解析供持剧本的消费方（数据形状优先）；生成入队另过路线闸门，跨族失配显式拒绝并给重拆指引；规范解析 fail-loud，删除全部历史兜底；每个消费方一条遍历表键的穷尽性测试。
- 原因/取舍：否决复合键注册表、否决把行为写入宽表、否决「缺失默认某模式」、否决正则拦截测试。
- 对 Linglong：【简化后采纳】Linglong 内容类型少，但「骨架知识一处定义 + 穷尽性测试 + 禁止二值兜底」可防同类静默丢数据。（P-04、P-06）

### ADR-0055 生成路线创建时锁定，宫格降为分镜路线内的装配选项
- 路径：`docs/adr/0055-generation-route-locked-at-creation.md` ｜ 状态：accepted
- 问题：路线（分镜图生视频 / 参考生视频 / 宫格）曾是可按集覆盖的三值，能力、估价、时长约束都要携带集上下文，口径不一。
- 决策：路线二值、创建时必选、之后不可变，由「任何写入面都没有该字段」结构性保证；宫格是分镜路线内的项目级开关（广告恒拒）；区分路线的判据是喂给视频模型的输入契约（单张首帧 vs 参考图集合）；剧本不带路线戳；存量由一次性迁移重编码；宫格开关不进 Agent 白名单。
- 原因/取舍：否决集级覆盖、否决剧本携带路线戳、否决读时映射兼容、否决宫格作为第三路线。
- 对 Linglong：【采纳】项目 brief 中锁定「首帧驱动 / 参考图驱动」路线，估价与执行同读一个字段。（P-02、P-06、P-07）

### ADR-0080 内容确认即把脚本规划转为正式脚本，提示词编写只填待编写分镜
- 路径：`docs/adr/0080-review-confirm-materializes-script-prompt-authoring-fills-pending.md` ｜ 状态：accepted（取代 0041、0075 的部分内容）
- 问题：0041 让同一集内容持久化两份（规划 + 正式脚本），下游结构编辑（增删分镜）会在下一次提示词编写时被静默撤销，还需要指纹、回填、合并一整套机制维持一致。
- 决策：提示词编写后正式脚本是该集唯一内容真相；确认动作把规划一次性机械转成整集正式脚本（已有脚本时即覆盖，以 danger 确认框列出将移除的分镜与产物去向）；提示词编写只给带「待编写」显式标记的条目补视觉层，点名重写才覆盖手改；确认后规划只读；之后的内容修改在正式脚本上做，原文只读展示、写入时校验为源文逐字子串；退役指纹与合并机制。
- 原因/取舍：否决把下游编辑收编回规划、否决保留指纹作优化、否决保留旧脚本备份。
- 对 Linglong：【采纳】「确认即物化、之后只有一份真相、待编写显式标记」比双份同步简单得多，建议 Linglong 从一开始就这样设计。（P-04、P-06、P-09）

## 8. 视频单元与提示词

### ADR-0064 视频单元以自由文本为唯一真相，参考图与发声读时派生
- 路径：`docs/adr/0064-video-unit-body-is-the-only-truth.md` ｜ 状态：accepted（两段由 0073 取代）
- 问题：参考生视频路线一个单元 = 一次视频调用，若参考图集合、发声条目与正文同时落盘，任何一条写路径漏掉重算就会用陈旧参考图生成。
- 决策：单元只落盘一段自由文本正文与编排时长；正文里的提及记号与台词记号决定一切，参考图集合、发声条目、说话人绑定在读时机械派生、不落盘、不进 LLM 输出；参考图顺序即首次提及顺序（即提示词中图 N 的编号），所有资产类型同一规则；只作说话人出现的角色只绑音色不出图；废除镜头数组与可手工编辑的引用列表。
- 原因/取舍：否决保留镜头结构、否决独立引用清单（等于承认正文说了不算）、否决按类型排序或补足参考图。
- 对 Linglong：【采纳】「派生物不落盘」可在结构上消除陈旧参考图问题；注意 Linglong 需设计自有的提及语法，不照搬 ArcReel 记号。（P-06、P-05）

### ADR-0070 提示词保留结构化与纯文本两种形态，实发文本只有一个渲染出口
- 路径：`docs/adr/0070-prompt-forms-and-single-rendering-exit.md` ｜ 状态：accepted
- 问题：分镜图/视频提示词可存为结构化或纯文本，若预览、准入、执行各自拼装，同一条提示词会因入口不同得到不同请求，还可能重复注入声明。
- 决策：两种形态都是正式内容、不承诺互转；每种媒体类型只有一个渲染出口负责注入画风、反向约束、参考图类型声明（含商品保真）与发声声明，且对已渲染文本幂等；产物依据收内容与形态，不收渲染包装与渲染器版本；精确请求复用另用执行敏感摘要。
- 原因/取舍：否决纯文本绕过渲染、否决把纯文本解析回结构、否决以实发文本作时效依据（改注入措辞会让全部产物变旧）。
- 对 Linglong：【采纳】「预览所见即执行所得」是 P-07 可审计性的基础。（P-07、P-12）

### ADR-0077 一个生成环节一份整段模版，轴差异用命名变体片段
- 路径：`docs/adr/0077-whole-prompt-templates-with-named-variant-partials.md` ｜ 状态：accepted
- 问题：全仓约 60 处提示词定义散在七种载体，同一风格字段四种句式、负向提示五套措辞；创作者看不到实际发出的完整提示词。
- 决策：每个生成环节恰一份模版文件，正文就是完整提示词、只留数据槽位；共享措辞抽成片段（两个以上环节使用才抽）；轴差异（源类型、资产类型、时长档等）用命名变体片段文件表达，模版内不比较轴值，条件只允许对槽位做真值判断；模版随核心库打包、不放进 Agent profile；模版目录作为构造依赖注入；变体族齐全性加载期校验，刻意为空用空文件表达；系统设置页可枚举全部模版源文；模版措辞升级不使产物 stale。
- 原因/取舍：否决模版内条件分支、否决放入 Agent profile、否决 include 标签、否决模块自行定位目录、否决全部列表由代码预渲染。
- 对 Linglong：【简化后采纳】「一环节一模版、提示词对运营可见、措辞不进产物依据」值得采纳；Linglong 的提示词必须自行撰写，严禁复制 ArcReel 模版文本。（P-07、P-12）

## 9. 资产与一致性

### ADR-0023 项目风格存模版展开快照，与风格参考图互斥
- 路径：`docs/adr/0023-style-template-expanded-snapshot.md` ｜ 状态：accepted
- 问题：只存风格模版 ID、生成时查表展开，会让已出片项目在模版升级后风格突变。
- 决策：选定模版时把整段画风文本展开写入项目并保留模版 ID 作来源；模版后续改动不回写老项目；风格为「模版 / 自定义参考图 / 无」三选一互斥，由写入路径保证。
- 原因/取舍：牺牲模版优化的自动传导，换取成片一致性。
- 对 Linglong：【采纳】品牌风格/视觉规范应以快照形式固化进项目。（P-02、P-05）

### ADR-0034 商品一致性双层锚点
- 路径：`docs/adr/0034-product-fidelity-dual-layer-anchor.md` ｜ 状态：accepted
- 问题：带货成片中商品必须忠实于真品（失真即虚假宣传风险），而 AI 重绘的 sheet 会让 logo、包装文字、材质漂移在源头固化。
- 决策：商品资产必有多张用户原图，原图永远是保真验收锚点并直接进入下游参考；标准化商品 sheet 可选，与其他 sheet 同一生命周期（可 stale、不自动重生）；分镜路线中商品参考二元注入（商品镜头全量且优先，氛围镜头零注入），且只在分镜阶段注入、视频请求不重复追加；参考路线按正文首次提及顺序注入、不排最前；商品原图上传保留原件字节不压缩；商品无独立审批状态字段。
- 原因/取舍：否决「弱注入」（参考图是强条件，给图又求别太像自相矛盾）；画风统一由项目风格承载而非商品图。
- 对 Linglong：【采纳】商业广告的核心保障：原图 = 验收锚点，是 P-05/P-13 与广告合规审核的基础。（P-05、P-13、P-09）

### ADR-0057 资产以名称为身份，重命名走级联重写
- 路径：`docs/adr/0057-asset-name-as-identity-cascade-rename.md` ｜ 状态：accepted
- 问题：剧本是 LLM 读写的文档，资产以专名被引用；改名如何处理。
- 决策：名称即身份，重命名是一次原子级联事务，改齐资产键、全部剧本引用与按名命名的文件；目标名冲突即拒绝；全局资产库与项目是快照关系不联动；不与进行中任务互斥。
- 原因/取舍：否决引入稳定 ID——会把解引用复杂度摊到每次生成与渲染的高频路径，级联把复杂度集中在低频改名。
- 对 Linglong：【待评估】Linglong 资产在数据库中（待确认是否已有 ID），可考虑「DB 用稳定 ID、剧本与提示词用名称」的混合；需权衡 LLM 可读性。（P-05、P-13）

### ADR-0066 资产图版式按下游消费定，角色保留三视图
- 路径：`docs/adr/0066-asset-sheet-layout-by-consumer.md` ｜ 状态：accepted
- 问题：资产图主要用作下游 i2i / r2v 的条件输入，版式应如何取舍。
- 决策：场景、道具、商品各出单张图，角色出三视图横排（依据是业界产品惯例而非一手证据，明确接受拼贴继承风险）；只保留正向的排除声明，不写解剖防崩与质量词；保留纯色背景（场景除外）；资产图生成必须显式指定宽高比；不设模板文本断言测试，靠人工 QA 对比。
- 原因/取舍：调研了多家图像供应商指南与论文证据；否决一资产多图（属资产模型议题）、否决按项目覆盖版式、否决裁切补偿层、否决 negative prompt 通道。
- 对 Linglong：【简化后采纳】「版式按下游消费定」「资产图必须显式指定比例」直接可用；具体版式应基于 Gemini 图像官方指南自行验证。（P-05）

### ADR-0072 角色衍生是子身份
- 路径：`docs/adr/0072-character-derivative-sub-identity.md` ｜ 状态：accepted
- 问题：一个角色只有一张资产图，表达不了换装、变身、易容。
- 决策：衍生挂在角色之下，共享名字、声音与说话人绑定，以「角色/衍生」形式引用；衍生没有原图与上传入口，只有一段相对本体的外观变化描述与一张由本体资产图编辑生成的图（0050 语义）；本体重生后衍生判 stale；同镜头可同时注入本体与多个衍生；纳入级联改名；机制通用建模但只对角色开启。
- 原因/取舍：否决衍生作为独立角色、否决「一切皆形态」、否决衍生写完整外观、否决衍生自带声音。
- 对 Linglong：【简化后采纳】短剧换装、广告多场景同一代言人都需要；可先只做「本体 + 编辑派生的形态图」。（P-05）

### ADR-0073 生成入口要求引用已登记且有资产图
- 路径：`docs/adr/0073-generation-entry-requires-registered-assets-with-sheets.md` ｜ 状态：accepted（取代 0064 两段）
- 问题：视频是最贵的生成，此前未登记的引用只警告并被丢弃、无资产图的角色退回原图，参考不完整时照常花钱。
- 决策：在生成入口（单条与整批准入）收紧：引用未登记或已删除的资产即阻断；角色、场景、道具、衍生无资产图即阻断，原图只作生成资产图的输入；商品维持原图直接进参考；编辑与保存仍只警告。
- 原因/取舍：写作时不逼作者先建资产，花钱时必须完整——阻断挪到生成入口后两者不再冲突。
- 对 Linglong：【采纳】「保存宽松、花钱严格」正对应 Linglong 的人工确认前置要求。（P-05、P-07）

## 10. 产物、版本与迁移

### ADR-0004 导入修复留在归档模块，不走保存统一入口
- 路径：`docs/adr/0004-import-repair-stays-in-archive.md` ｜ 状态：accepted
- 问题：有人建议把归档导入的「急救式修复」并入项目管理器，让导入与保存走同一套保证。
- 决策：否决该建议——急救修复是导入特有的 I/O，契约（使劲修 + 缺定义拦截）与保存的「不更坏」不同；真正要收敛的只是重复的形状常量：规范资源路径统一成一张表，内容模式到字段名的分派改调骨架注册表。
- 原因/取舍：记此 ADR 是为了拦住未来「好心合并」。
- 对 Linglong：【简化后采纳】若 Linglong 做项目导入/复制，「导入修复与日常保存分离、资源路径规则只有一处」适用。（P-13、P-10）

### ADR-0022 project.json 文件级 schema 版本化 + 启动时逐级幂等迁移
- 路径：`docs/adr/0022-project-json-schema-versioned-startup-migration.md` ｜ 状态：accepted
- 问题：靠读时兼容旧字段会让旧形状无限残留、读路径分支越积越多。
- 决策：顶层 schema 版本 + 迁移注册表，启动时逐级跑纯函数迁移（先备份、原子写回、级联迁移剧本），单项目失败隔离；导入路径复用同一迁移链；多文件级联迁移在同级 staging 树完成后整目录替换，崩溃残留由启动扫描认领恢复；带磁盘容量预检。
- 原因/取舍：迁移就地改写不可逆，换取数据形状收敛。
- 对 Linglong：【简化后采纳】Linglong 数据在 DB 中，DB 迁移工具已覆盖；但 JSON 类字段（脚本、分镜结构）同样需要显式版本号 + 一次性迁移，而非读时兼容。（P-03）

### ADR-0062 产物生命周期以产物清单为唯一口径
- 路径：`docs/adr/0062-artifact-lifecycle-and-currency.md` ｜ 状态：accepted
- 问题：用户为每件产物付过费，系统必须回答「它在不在」与「它还对不对得上当前内容」；扫目录只能答前者，给每件产物存状态字段又要求每次内容变化同步回写。
- 决策：项目内一份产物清单只登记产物身份、路径与生成依据摘要（直接消费的正式内容与直接上游产物的规范化哈希），**不存状态**；四态（current / stale / missing / blocked）在读取时比对当前投影得出。依据只收正式内容，模型、分辨率、seed、渲染器版本等「下次怎么生成」的意图不进依据；但旁白的音色语速等决定成品听感，进依据。升级补录一律判 current；stale 可查看、可参与成片与导出，不自动重生；不指定目标的生成只补 missing；blocked 一律 fail-loud 不降级为 missing。任务结果、产物时效、批量准入结论、逐项执行结果四条状态轴并列、绝不合并。schema 版本是唯一激活门，迁移失败持久化为阻断裁决（可读不可生成）。清单用项目级跨进程锁、全量原子替换。
- 原因/取舍：否决扫目录、否决条目存状态、否决配置一律进依据、否决补录后判 stale 或引入「来历不明」第三态、否决 stale 自动重生、否决迁移失败静默降级、否决剧集级锁；明确接受清单体量随项目线性增长。
- 对 Linglong：【采纳】这是 P-09「所有 take 可见、不静默覆盖」与 P-12 审计的底座；Linglong 可放在 DB 表而非 sidecar 文件，但「依据摘要 + 读时判定 + 四轴不合并」要原样保留。（P-03、P-07、P-09、P-10、P-12）

### ADR-0075 旧媒体版本记录的来源由迁移按当时状态投影补写
- 路径：`docs/adr/0075-legacy-media-provenance-projected-at-migration.md` ｜ 状态：accepted（无计划剧本部分由 0080 取代）
- 问题：早期视频版本记录缺少类型化来源，产物清单补录把「解析不出」当「不存在」，用户升级后看到视频计数归零。
- 决策：一步迁移按迁移那一刻的项目状态、用与时效比对同一个依据构造器，为仍被引用的旧视频补写全部来源字段并标记补写时间，因此补录即 current；读路径不区分补写与冻结记录；旁白音频不补写（依据含 TTS 设置，任何投影都是编造），进迁移报告；投影失败项进报告而非让整项目失败。
- 原因/取舍：否决放宽读侧接受降级依据（即 0062 否掉的第三态）、否决不加补写标记、否决一条坏记录拖垮整项目。
- 对 Linglong：【简化后采纳】Linglong 现有产出在引入 lineage 时同样需要「一次性按当时状态投影 + 标记为回填 + 无法投影者入报告」。（P-12）

### ADR-0009 计费定价改为代码级声明式
- 路径：`docs/adr/0009-declarative-model-pricing.md` ｜ 状态：accepted
- 问题：费率散落在十余张类属性字典里，按供应商长串 if 路由，新增供应商若漏分支，视频会静默按另一家的费率计价。
- 决策：定价作为模型条目的字段并进注册表（每模型单一真相源），计算策略按定价形态标签派发并放独立模块；下线模型用隐藏标记保留条目以覆盖「入队后被下线」边角；全量迁移现有供应商、以测试对拍旧值；运行时改价不做。
- 原因/取舍：关键事实——费用在调用完成时快照冻结，历史记录不依赖费率表，因此无需历史费率库；改促销价需重部署是有意取舍（成本只用于预估与内部记账）。
- 对 Linglong：【采纳】Vertex 各模型单价以声明式登记、完成时快照进调用记录；价格数值需以 Google 官方价目为准。（P-12）

### ADR-0053 费用归属以记账 key 为强证据
- 路径：`docs/adr/0053-cost-attribution-ledger-key-primary.md` ｜ 状态：accepted
- 问题：费用要归属到集与剧本条目，但条目 ID 不全局唯一、可被编辑与复用。
- 决策：以冻结在调用记录上的资源 ID 为强证据，同一 (key, 费用类型) 按币种汇总、一次估算只认领一次；宫格按覆盖条目均摊；无法被当前剧本认领的历史费用不丢弃，统一进项目级「未归属」桶，能解析出集号的在集级另展示一份视图（不得叠加求和）；文本调用与资产图另行汇总。
- 原因/取舍：否决为条目引入全局唯一身份（迁移成本不成比例）；ID 不唯一是已知且接受的限制，审查中「先校验唯一性再归属」的建议应被驳回。
- 对 Linglong：【简化后采纳】Linglong 若用 DB 主键可天然避免 ID 复用，但「未归属桶不丢钱、视图与合计分离」的口径应保留。（P-12）

### ADR-0076 使用记录是供应商调用的投影，任务与调用一对多
- 路径：`docs/adr/0076-usage-record-is-projection-of-provider-calls.md` ｜ 状态：accepted
- 问题：「使用记录」页要把排队/进行中任务与已结束调用放进同一时间线，直觉做法是共用一个存储实体。
- 决策：调用表只记真实发生过的对外请求（费用与用量最小单位，可空地指向服务的任务并说明来源），任务表只管意图与调度；「使用记录」是读模型，进行中区来自任务、终态来自调用，前端拼接；调用状态加「已取消」以免被记为失败。
- 原因/取舍：钱按请求花不按意图花；否决入队即建调用行（会出现从未请求的取消行）与读侧复合主键拼表。
- 对 Linglong：【采纳】P-12 审计的基础数据模型：任务 1 : N 调用。（P-12、P-11）

### ADR-0020 运行时状态合并为单一异步 ORM 数据库
- 路径：`docs/adr/0020-runtime-state-single-async-orm-db.md` ｜ 状态：accepted

- 对 Linglong：【采纳】Linglong 已以 DB 为中心（Cloud SQL 迁移计划见 LinglongLab 文档，待确认），保持任务、调用、产物登记同库同事务。（P-03、P-11）

### ADR-0021 开源版预埋多用户数据模型，但不实装多租户
- 路径：`docs/adr/0021-multi-user-preembed-scope-query.md` ｜ 状态：accepted
- 问题：后期给在用表加非空外键并回填，代价远大于一开始就预埋，且会让开源与商业版 schema 分叉。
- 决策：任务、调用、API Key、会话表带用户字段（恒为默认用户），建用户表，仓储基类提供空实现的查询改写点，商业版覆盖注入过滤；不做目录隔离、登录、配额与后台；认领任务用原生 SQL 是已知需覆盖的例外。
- 原因/取舍：接受一批看似无用的空实现，勿当死代码删除。
- 对 Linglong：【简化后采纳】Linglong 是内部多用户产品，应直接实装真实的用户/团队作用域，而不仅是预埋。（P-01、P-12）

### ADR-0088 数据根分层：项目收进 projects/ 子目录
- 路径：`docs/adr/0088-data-root-layered-projects-subdirectory.md` ｜ 状态：accepted（取代 0074 部分）
- 问题：项目与数据库、全局资产、用户记忆平铺在数据根，靠点/下划线前缀区分；漏加前缀的目录被当成项目列出且删不掉，日志与凭证无处安放。
- 决策：项目收进数据根下的专门子目录，其余运行数据以无前缀名字并列；项目只有一处判定（该子目录下合法名称且含项目文件）；原地嵌套不改部署配置；Agent 对数据根默认拒读，只放行当前项目与当前用户记忆；不支持降级。
- 原因/取舍：否决维持平铺只集中判定、否决换新默认数据根（会让部署「项目全部消失」）、否决藏进隐藏目录、否决保留旧前缀名字。
- 对 Linglong：【简化后采纳】对应 GCS bucket 前缀规划：「什么是项目」只在一处判定，系统数据与项目媒体分层。（P-01、P-13）

## 13. 前端、实时与认证

### ADR-0005 SSE 流暴露为 async 上下文管理器，消费方空闲时自检断线
- 路径：`docs/adr/0005-sse-stream-async-context-manager.md` ｜ 状态：accepted（事件形态由 0046 修订）
- 问题：流接口曾直接暴露队列，漏写 finally 即订阅者泄漏；而仅改成 async generator 也不能保证断线及时清理——取消信号在生成器停在 yield 时够不到嵌套 finally。
- 决策：接口形态为 async 上下文管理器，由退出钩子承载注销；消费循环靠心跳/空闲哨兵定期醒来主动检查客户端是否断开并正常退出，不赌框架的取消注入；两条流事件形态各异、按流处理。
- 原因/取舍：上下文管理器与主动自检缺一不可。
- 对 Linglong：【采纳】FastAPI 侧任何任务进度流都应这样写，避免订阅泄漏。（P-03、P-11）

### ADR-0024 媒体缓存用文件 mtime 作 cache-bust，版本文件设 immutable
- 路径：`docs/adr/0024-media-cache-mtime-fingerprint.md` ｜ 状态：accepted
- 问题：会话级计数器在刷新、跨会话、虚拟滚动重挂载时反复下载，且新会话计数可能对应已变内容。
- 决策：资源 URL 带文件 mtime 指纹，带指纹或位于版本目录的请求设一年 immutable 缓存；指纹随项目 API 与事件下发。
- 原因/取舍：immutable 发出后客户端长期缓存，所以指纹必须随内容变。
- 对 Linglong：【简化后采纳】若媒体放 GCS，用对象 generation / etag 作指纹等价实现。（P-09、P-14）

### ADR-0035 前端供应商配置按消费时点拉取，不持久缓存
- 路径：`docs/adr/0035-frontend-provider-config-fetched-fresh-no-cache.md` ｜ 状态：accepted
- 问题：模块级缓存从不失效，成了会漂移的第二真相源（设置里加了时长，项目页仍显示旧值）。
- 决策：取数函数完全无状态，每次消费直接重拉，删除缓存、in-flight 去重与失效函数。
- 原因/取舍：多拉几次小 JSON；否决 zustand store（本路由结构下是过度设计）。
- 对 Linglong：【采纳】能力与时长等可变配置在 Next.js 端按页拉取，不做长寿命缓存。（P-02、P-07）

### ADR-0059 认证要求由路由注册处单点声明
- 路径：`docs/adr/0059-router-level-auth-single-truth-source.md` ｜ 状态：accepted
- 问题：认证曾靠每个端点签名各自声明，供应商配置与凭证路由整组漏声明，未登录即可读写凭证并劫持生成后端。
- 决策：需要认证的 router 在注册时统一挂认证依赖；公开端点与自带认证端点放在单独的 router 对象里；注册区块即公开面清单；由集成测试从 OpenAPI 枚举全部操作、对豁免清单外逐一断言 401。
- 原因/取舍：否决 app 级全局依赖 + 豁免表（依赖框架私有表示）、否决端点装饰器标记公开面、否决合并「公开」与「自带认证」概念。
- 对 Linglong：【采纳】FastAPI 侧可直接照此模式 + 全量 401 枚举测试。（安全基线，无对应 P 项）

### ADR-0071 浏览器原生请求的凭证载体
- 路径：`docs/adr/0071-browser-native-request-credential-carrier.md` ｜ 状态：accepted
- 问题：浏览器原生请求带不了认证头，SSE 曾把长效会话 JWT 放进 URL 查询参数并落进访问日志。
- 决策：SSE 改由 fetch 带认证头消费（前端自行解析、续传与重连），删除 URL token；静态媒体维持匿名可读但严格限定目录与扩展名白名单并加 nosniff；项目导出仍用短时效下载 token。
- 原因/取舍：单管理员自托管威胁模型；否决 Cookie 认证、否决短时效目的票据、否决前后端分离部署。
- 对 Linglong：【简化后采纳】SSE 走 fetch + 认证头直接适用；媒体匿名可读**不适合** Moloco 内部环境，应改用签名 URL。（P-10、P-03）

### ADR-0085 项目事件保留显式事件与快照差分两个来源
- 路径：`docs/adr/0085-project-events-dual-source-registry-derived-projection.md` ｜ 状态：accepted
- 问题：快照差分用一份手挑字段的影子 schema，新资产类型与许多字段变化比不出来，Agent 改完界面停在旧状态；轮询还顺带写盘。
- 决策：显式事件负责快照看不见的事实（同路径字节替换、任务语义），快照差分兜底其余；投影按资产类型注册表派生、整条目比对，只排除每次写都变的元数据与生成资产字段；衍生单独成事件；轮询只读。
- 原因/取舍：否决每个写入口自报前后（第三来源、重新引入对账问题）、否决字段白名单比对（多报一次的代价远小于漏报）。
- 对 Linglong：【简化后采纳】「任务完成走显式事件 + 状态变化整条目差分兜底」可保证 P-03 刷新不丢状态。（P-03）

## 14. 工程治理与文档

### ADR-0060 第三方 API 文档采用官方链接索引而非正文镜像
- 路径：`docs/adr/0060-official-links-replace-vendored-api-docs.md` ｜ 状态：accepted
- 问题：把供应商与 SDK 文档正文、价格表镜像进仓库会随上游更新漂移。
- 决策：只维护按规范 ID 的官方链接与代码入口；运行时数值仍由注册表与后端声明持有；历史语义以固定版本源码或契约测试作证，测试 fixture 保持最小。
- 原因/取舍：失去离线正文与稳定行号。
- 对 Linglong：【采纳】与本仓库 CLAUDE.md「模型名/端点以官方文档为准、不猜」一致。（P-07）

### ADR-0063 领域术语一次性迁移，不保留兼容别名
- 路径：`docs/adr/0063-domain-glossary-one-time-migration.md` ｜ 状态：accepted
- 问题：术语表格式不一，混有机制说明与通用技术概念。
- 决策：术语表全量改写为短词条（规范产品名 + 机器标识、1–2 句定义、应避免的同义词）；不保留旧名别名；机制类内容移到 ADR 与代码文档字符串；代码符号不跟着改名；存量旧名只在顺手修改时更新。
- 原因/取舍：别名一旦存在就无法收敛；分批替换易产生新旧交叉引用。
- 对 Linglong：【采纳】Linglong 需要自己的术语表（parity 方法已要求「Linglong-owned terminology」），可借鉴其格式纪律但不复制其词条。（P-02、P-14）

### ADR-0084 保留核心库与服务端两个根，目录按领域术语表分包
- 路径：`docs/adr/0084-keep-lib-and-server-roots-group-by-glossary.md` ｜ 状态：accepted
- 问题：核心库顶层平铺 130 个散模块、服务层 30 个平铺模块，目录与术语表不同构。
- 决策：保留两个根与启动入口不变；按术语表章节分包，不建 utils/common，纯技术工具集中在 infra；判据是「模块是什么」而非「谁在用」；一次性按映射表搬迁、不留兼容 re-export；包间环如实登记为存量，不靠改名或拆文件消除。
- 原因/取舍：否决按领域垂直切片（会打散工具运行时并让核心依赖交付层）、否决合并单一根包或改名。
- 对 Linglong：【简化后采纳】`apps/api/app/ai_video` 已有分层；「核心逻辑不知道 HTTP / Agent / SSE 的存在」这一分界值得作为模块评审标准。（无对应 P 项）
